# 已确认需求快照

> 本文件采用覆盖式存档，只保留当前已经明确确认的业务需求，不记录历史版本，也不把建议方案自动视为已确认需求。

- 最后更新：2026-07-13
- 产品名称：像素引擎（PixelEngine）
- 后端技术栈：Python 3.14 + FastAPI + PostgreSQL 18 + Redis Server 8+ + Taskiq
- 关联设计：[business-design.md](./business-design.md)

## 1. 用户账户

- 系统需要登录和注册功能。
- 用户使用邮箱和密码注册账户，注册后可以直接登录。
- 首版不做邮箱验证码、验证链接或其他邮箱所有权验证，不接入邮件验证服务。
- 普通用户拥有独立账户和额度余额。

## 2. 角色

系统首期至少包含两种角色：

- 普通用户。
- 超级管理员。

超级管理员负责平台级配置，普通用户不能查看或修改上游渠道凭证。

超级管理员还需要具备用户管理能力：

- 分页查看和搜索用户列表。
- 查看用户基础信息、账户状态、额度余额、额度流水、充值订单和生成记录。
- 启用或停用普通用户账户，并使被停用用户的现有会话失效。
- 手动增加或扣减用户额度，每次调整必须填写原因。
- 每次用户状态变更和额度调整都必须写入管理员审计日志。
- 手动扣减额度后不允许用户余额小于零。

## 3. 额度充值

- 用户可以购买平台额度。
- 初期兑换比例固定为 1 元人民币兑换 1 平台额度。
- 支付使用 EPay 标准协议格式。
- EPay 网关和商户配置由超级管理员填写和维护。
- 支付成功后增加用户额度。
- 支付回调和额度入账必须由后端处理，不能由前端支付结果页面直接增加额度。
- 同一个支付订单或支付回调不能重复入账。

## 4. 图片模型厂商

平台需要支持多个图片模型厂商，首批目标至少包括：

- Google 的 Banana / Nano Banana 图片模型系列。
- xAI 的 Grok 图片模型系列。
- OpenAI 的 GPT Image 图片模型系列。

厂商是模型和渠道的归属。创建渠道时必须绑定一个厂商。

## 5. 上游渠道

超级管理员可以：

- 创建多个上游渠道。
- 为渠道选择所属厂商。
- 填写渠道 Base URL 和上游 API Key。
- 手动从渠道拉取最新模型列表。
- 从拉取结果中选择图片模型加入平台模型池。

同一个厂商可以拥有多个渠道。普通用户不直接接触渠道 Base URL 和上游 API Key。

## 6. 模型池

- 只有已经加入模型池并启用的模型才能供普通用户调用。
- 平台模型需要有稳定的平台模型 ID。
- 平台模型归属于一个厂商。
- 超级管理员可以设置和调整每个模型的用户单价。
- 平台负责把用户选择的平台模型路由到该厂商下的可用渠道。

### 6.1 渠道路由

- 渠道具有管理员配置的优先级、权重和最大并发数。
- 平台实时计算渠道当前请求数和负载因子。
- 路由首先选择优先级最高的可用渠道组，再在同优先级渠道中按权重和当前负载选择渠道。
- 当高优先级渠道全部不可用或达到并发上限时，可以溢出到下一优先级。
- 超时、限流、网络错误和上游服务错误可以切换到其他渠道。
- 参数错误、内容审核拒绝和其他确定性业务错误不能通过切换渠道重复请求。
- 渠道连续失败达到阈值后进入冷却状态，冷却结束后通过探测请求恢复。

## 7. 图片生成计费

计费单位已经确定为请求图片数量。

```text
消费额度 = 模型单价 × 请求图片数量
```

- 前端提交请求时需要携带平台模型 ID 和请求图片数量。
- 后端在请求创建时保存模型单价、请求图片数量和应扣额度快照。
- 上游因协议限制拆分出的内部请求次数不影响用户计费。
- 请求成功生成多少张图片就结算多少张；失败的图片数量按该请求的模型单价退回对应额度。
- 全部失败时退回本次请求的全部已扣额度，部分失败时只退失败图片对应的额度。

## 8. 网页端模型选择

- 图片生成参数栏需要增加平台模型 ID 选择项。
- 模型选择器的数据来自后端模型池。
- 默认记住用户上次选择的平台模型。
- 已停用或已移出模型池的模型不能继续提交新请求。
- 首版不建设图片对象存储，生成图片和画廊原图继续保存在浏览器本地。
- 服务端仍保存生成请求、计费、状态和审计记录，但不承诺跨设备恢复图片原文件。
- 后端可以使用有过期时间的临时文件缓存向当前用户交付生成结果，但不能把图片二进制长期存入 PostgreSQL 或 Redis，也不能向用户暴露上游原始 URL。
- 后续对象存储确定使用 MinIO，并在对应版本设计图片上传、访问控制、生命周期和跨设备历史。

## 9. 用户 API Key

- 普通用户可以创建供外部系统调用的平台 API Key。
- 创建 API Key 时必须选择一个厂商。
- 使用该 Key 时，请求只能调用其绑定厂商下已进入模型池并启用的模型。
- 后端根据厂商和平台模型选择对应渠道。
- API Key 消费用户自己的平台额度。
- 上游渠道 API Key 与用户创建的平台 API Key 是两类不同凭证。
- 用户平台 API Key 的原文只应在创建时展示一次，后端保存不可逆哈希。
- 平台不提供 BYOK，不允许普通用户填写自己的上游 API Key 或 Base URL 直连厂商。
- 现有前端中的 BYOK、API Profile、自定义供应商和上游直连能力需要永久删除，不保留兼容入口。

外部 API 不使用单一协议强行兼容所有厂商：

- OpenAI 系列平台模型的外部接口完整兼容 OpenAI 图片 API 协议。
- Gemini 系列平台模型的外部接口完整兼容 Gemini 官方协议。
- Grok 系列平台模型的外部接口完整兼容 xAI/Grok 官方协议。
- 请求和响应格式、错误结构、流式或异步语义应分别遵循对应厂商协议。
- 外部请求仍使用平台模型 ID、平台 API Key 和平台额度，不暴露实际上游渠道。

## 10. 后端权威边界

以下操作必须由 FastAPI 后端完成：

- 用户身份和角色校验。
- 额度检查、扣费和结算。
- EPay 签名、回调校验和入账。
- 模型池可用性校验。
- 渠道选择和上游请求。
- 上游 API Key 保管。
- 用户平台 API Key 校验。
- 生成请求和计费记录。
- 异步生成任务调度、渠道并发控制、任务重试和卡住任务恢复。

普通用户前端不能通过提交任意 Base URL 或上游 API Key 绕过平台路由和计费。

系统确定使用 Taskiq 0.12+、taskiq-redis 1.2+、redis-py 8.x 和 RedisStreamBroker 处理异步任务，不采用 Celery 或 ARQ。PostgreSQL 18 必须作为生成任务、渠道尝试和计费结果的权威数据源，不能把 Redis 或 Taskiq Result Backend 作为业务事实来源。

## 11. Agent 模式

- Agent 多轮对话模式永久删除。
- 前端不再提供画廊/Agent 切换入口。
- 设置页不再提供 Agent API、工具轮次、Web Search 或 Agent 专属配置。
- 平台后续不为 Agent 保留兼容入口或计费方案。

## 12. 尚未确认，不纳入本快照

以下内容仍需单独讨论：

- 在没有邮件验证服务的前提下，是否提供自助忘记密码功能；首版可以改为超级管理员签发一次性重置凭证。
- MinIO 对象存储和跨设备图片历史的具体实施版本。
- 各厂商兼容 API 的最终路径前缀、版本号和协议测试基线。
